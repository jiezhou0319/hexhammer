# hexhammer 规划文档集评审报告

**评审对象**：`C:\code\hexhammer\docs` 下全部规划文档（00-vision / 01-research / 02-architecture / 03-roadmap / 04-tasks-m1 / 05-extensibility / 06-game-design / 07-combat-math / 08-troop-design / 10-params-test / 11-research-wc4），并交叉核对仓库根 `README.md` 与 `project.godot`。**按任务要求排除 09-open-questions.md**（仅在涉及门禁耦合时提示风险，不作内容评审）。
**评审基准**：README 效力链（00 > 06 > 07/08 > 02 > 03/04；09 仅台账；01/11 非拍板）+ 各文档修订记录（含日期）。
**评审方式**：逐份全文阅读 + 跨文档交叉核对 + 对仓库实际文件（`project.godot`、`tools/`）抽查验证。

## 核心发现

这份规划的整体架构是**高质量的**：效力链机制、修订记录留痕、07 的"公式/常量/工具三同步"数值纪律、10 的测试版参数载体、03 把"证伪优先"写进里程碑、11 的逆向风险警示（并已在 07 落地钳制）都体现了成熟工程自觉。**主要问题不在"想得不对"，而在"改向太快而文档同步不均"**：v1→v5 的多轮定位变更（skirmish→部队级→大地图→RTwP）留下了三类隐患——① 旧口径残留未被统一标注（含 1 处与仓库实际不符的**事实性错误**、1 处不可达的兼容性声明）；② 03/04 的排期、砍段次序、验收口径三者存在**互相击穿**的断点（验收项需要的兵种不在该里程碑范围内；砍段方案直接推翻里程碑定义）；③ 05 的扩展性门禁建筑在已被 00 v5 取消的"战斗实例 vs 战役层"二分之上，M3 将领养成可能无处落脚。以下按五个维度逐项列出，均附证据与理由。

### 2.2 理由与判断

- **S1 是排期哲学问题，不是估算问题。** 一个"存在性判断"型项目的最优顺序是**用最短路径先证伪**，而当前方案把 3~6 周的图形学/表现层投入放在证伪之前。M1a 的可复用性论证（"内核证伪后地形仍保留"）成立，但它论证的是"沉没成本可控"，不是"顺序合理"。**建议**把 M1b-T1 之后的"最小内核沙盒 + 粗糙地图"提前到 M1a 之前做 1~2 周的证伪 spike（可复用 M1a 的一半工作量），或把 M1a 的高程档位/美术并行分支明确砍到证伪之后。
- **S2 必须先统一口径再谈排期。** 04 自称"M1a 收尾用实测周数回填后续"，这是对的；但在此之前，3~6 周 / 3~5 周不构成可承诺的排期。**建议**把"半天~两天"明确为"有效工时（如 3h 单元）"，并标注"该估时对应 10~15h/周"。
- **S3/S4 是最危险的一类断点——"计划内部互相击穿"。** 砍段方案推翻自身定义（S3）、验收项依赖范围内不存在的兵种（S4），意味着 M1b 在纸面上就无法"按既定口径收尾"，实际执行时必然临场改口径，届时"证伪结论"的可信度会打折。**建议**：① 统一砍段次序并标注"降级后验收口径如何随之变化"，禁止出现"降级击穿定义"；② M1b 验收的"风筝"改为"骑枪/长枪的机动-追击窗口"等范围内可验证项，或把骑弓纳入 M1b 阵容（骑弓机制本就需要 10 §2/§3 的双费+反击系数，成本不高）。
- **S5/S6/S7 共同指向"关键路径风险后置"。** 判断工具在末端、拍板在门禁处却无工时、验证能力（存档）不在本期——三者叠加会让 M1b 收尾期变成高不确定性窗口。建议把"最小自战对表"和"最简快照（仅 `BattleState` 序列化）"前移。

### 3.2 理由与判断

- **C1/C2/C3 是"防患于未然"的核心项，属于必须在 M1b 动工前收口的。** 参考 11 §1.2 的 WC4 教训：加法百分比聚合最终会算出负伤害，本项目虽已加钳制，但"钳制区间是否够用"取决于"乘区总预算"——目前没有任何一处文档给出了叠加上限的计算（07 §3 的修正层设计稿彼此已是乘法叠加，再加 08 的机制层与装备/特化）。同理，反击率是"隐藏可变状态"，若不明确归属，M2 存档与自战重放都会出不一致 bug，且这类 bug 极难排查（11 §1.4/§1.7 也提示"修正对象的归属要在实现层显式命名""钳制责任唯一化"）。
